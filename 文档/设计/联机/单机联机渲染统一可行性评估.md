# 单机 / 联机渲染统一 —— 可行性评估与实施计划

> 目标问题：单机与联机是**两套渲染实现**，同一个逻辑 bug 会在两边以不同形态出现、也要修两遍。
> 本文只做评估与计划，**不含任何代码改动**。所有结论基于当前代码实况（2026-10-19 通读）。

---

## 0. 结论（TL;DR）

**可行性成立，而且比"重写一个渲染层"轻得多**——因为"单机 = 本进程服务端 + 本机客户端投影 + 快照渲染"这条链路**在工程里已经跑通并有生产入口**（`LocalHostServer` 的「建立主机」、`NetworkMatchLauncher.StartLocalLoopback`）。统一不是造新架构，而是把已有链路喂给单机。

但有 3 个硬点、1 个真正的成本、1 个必须提前否掉的产品前提：

| 类别 | 内容 | 性质 |
|---|---|---|
| 硬点 1 | **热座双视角**：联机是"一人一副手牌 + 按座位过滤"，单机是"同屏双人、两副手牌都明牌" | 需改造（已有不过滤分支可用，缺"双份合法性投影"） |
| 硬点 2 | **座位↔会话 1:1**：`MatchHost` 强制一连接一座位，单机要一连接两座位 | 需改造，且是**唯一安全边界变更** |
| 硬点 3 | **决策请求的归属与超时**：客户端丢弃非本座位请求；服务端 30~60s 自动取消 | 需改造（否则单机"想太久被自动取消"） |
| 真正的成本 | **全量重建的手感**：每步操作销毁重建全部 CardUI（桌面可接受，Web 可能明显卡顿） | 需先量化（P0 实验），再决定投入 |
| 产品前提 | 单机是否**必须保留同屏热座**。若"单机"只是一个人玩，直接复用「建立主机」+ BOT 即可，**改造成本接近零** | 需拍板 |

**建议路径**：先做 P0（量化实验）+ P1（布局共用件）+ P2（双端对拍机制），拿到数字和护栏后再决定是否全量切换（P3–P5）。不建议一次性大爆炸切换。

## 1. 现状：两套渲染的准确描述

### 1.1 对照表（代码实况）

| 维度 | 单机 | 联机 |
|---|---|---|
| 入口 | `GameManager.GameState.Arena` → `Scenes/Arena/Arena.tscn` | `OnlineArena` → `Scenes/Net/OnlineArena.tscn` → `OnlineArenaEntry` |
| 视图类 | `Arena`（+ `Arena.Events/Layout/Mask/BadgePeek`，共 **5778 行**） | `ArenaOl`（**4835 行**） |
| 模型来源 | 场景内 `GameInitializer` 节点，`_Ready` 里 `InitializeAll()`（**真实权威 Manager**） | `ClientMatchView` 里 **9 个投影 Manager**，只读、不结算 |
| 渲染驱动 | **事件增量**：`ZoneManager.OnCardMoved → SyncCardUIToZone`、`OnPostMove → 派生 UI`、`TurnManager.OnPhaseChanged…` | **快照全量**：`ApplySnapshot → Rebuild*/ArrangeAll` |
| 合法性来源 | **UI 本地现算**：`TurnManager.CanDeployCovert`、`CardManager.IsLegalPlayTarget` | **服务端投影**：`snap.View`（`LegalityProjection`），客户端只读 |
| 决策通道 | `IInputGateway` 未注入 → 本地 `IGameUIHooks` / `ITriggerView`（Arena 实现）同步弹窗 | `NetworkInputGateway` 发 `ChoiceRequest`，UI 回 `ChoiceResult` |
| 行动者身份 | 由**手牌容器**推断：`int playerId = inHand2 ? 2 : 1`（`CardDragController.cs:158`） | 固定 `_localPlayerId`（座位） |
| 视角 | 固定：P1 在下、P2 在上 | **视角归一**：`ViewMirrored = _localPlayerId == 2`，本方恒在下（`ArenaOl.cs:60-105`） |
| 布局 | `Arena.tscn` | `ArenaOl.tscn`——**从 Arena.tscn 复制**，容器/按钮坐标一致（实测 diff 仅少 4 个节点） |

> 布局同源这点很关键：视觉对齐的返工风险远小于"从零画一套 UI"。

### 1.2 两套实现各自的"bug 类"

- **单机（事件增量）的典型 bug**：漏订阅 / 漏刷新 / 刷新顺序错 → UI **永久漂移**（某张卡错位、横置不刷新、附属叠错）。这类 bug 在联机几乎不会出现，因为下一次快照会全量重建把它冲掉。
- **联机（快照重建）的典型 bug**：重建时丢本地态（选中/hover/拖拽被打断）、重建开销与闪烁、服务端投影字段漏下发导致"客户端判断与服务端不一致"。

所以"统一到快照"本质是**用"自愈的重建"替换"易漂移的增量"**——这正好对应用户感受到的"单机 bug 类型"。

### 1.3 已经存在的"统一地基"（可直接复用，不需要新造）

| 组件 | 位置 | 现状 |
|---|---|---|
| 服务端对局宿主 | `Script/Net/Godot/MatchHost.cs` | 装配 Hub/网关/快照下发，已被大厅与单场启动器共用 |
| 进程内回环传输 | `Script/Net/LoopbackTransport.cs` | 会话寻址、无需 socket，已有测试覆盖 |
| 客户端投影 | `Script/Net/Godot/ClientMatchView.cs` | 9 个投影 Manager + 快照应用 + 消息分发 |
| 断网/本机服务端 | `Script/Net/Godot/LocalHostServer.cs` | 「建立主机」= 进程内起 `LobbyServerHost`（真实 WebSocket） |
| 单进程"服务端+客户端"启动器 | `NetworkMatchLauncher.StartLocalLoopback()` | **已经是"房主即服务端"的原型** |
| 不过滤快照 | `GameInitializer.BuildSnapshotFor(viewerPlayerId)`；`SnapshotFilter.ForPlayer(full, ≤0)` 直接返回完整快照 | 支持"两份手牌都明牌" |
| 快照差异 → 表现层事件 | `SnapshotDiff` + `ArenaOl.RouteRenderCommands` | 动画触发源的骨架已留 |

## 2. 目标架构（统一后）

```
单机（同一进程）
┌──────────────────────────────────────────────────────────────┐
│  权威侧：GameInitializer + MatchHost（本地同桌模式）            │
│    IntentHub / NetworkInputGateway                            │
│         ▲ PlayerIntent(座位=被操作卡所属玩家)                   │
│         │ ChoiceRequest(按 request.PlayerId 归属，本地不超时)   │
│         ▼ 不过滤快照 + 双份合法性投影                            │
│  投影侧：ClientMatchView（9 个投影 Manager）                    │
│         ▼                                                     │
│  表现层：ArenaOl（viewSeat=0 同桌模式，不镜像；两副手牌都可拖）    │
└──────────────────────────────────────────────────────────────┘
联机 = 同一张图的"权威侧在别的进程、快照按座位过滤、本地座位固定"
```

**核心收益**：`ArenaOl` 成为**唯一渲染实现**。之后任何渲染/交互修复只写一处，单机与联机同时生效；`Arena`（5778 行）退役，净减一半渲染代码。

## 3. 五个必须解决的技术点（含方案与影响面）

### T1 · 热座的信息可见性与合法性投影

- **现状**：`MatchHost.PushSnapshot` 逐座位 `ForPlayer(snap, seat, view)`（`MatchHost.cs:289-295`），一份快照只带**一份** `View`；`ArenaOl.ClientLegalityView => _matchClient?.LastSnapshot?.View`（`ArenaOl.cs:2313`，唯一读取点）。
- **方案**：
  1. 单机走 `BuildSnapshotFor(0)`（不过滤）。已验证该分支可直接返回完整快照；`ArenaOl.RebuildInto` 对非 `IsHidden` 的卡一律画正面（`ArenaOl.cs:4423-4450`），所以**两副手牌天然可明牌显示**，无需新增字段。
  2. `GameSnapshot` 增一份"多视角"承载（`Views[seat]`，或单机专用 `View2`），单机填两份。`ArenaOl` 的读取点只有一个属性，按"当前行动者"切换即可。
  3. **不要**让单机客户端本地重算合法性——`ClientServerParityTests` 记录的历史坑（JC005/JC020/JC068/JC001）正是"客户端本地算 → 输入缺失 → 两端结论不同"。必须继续"服务端算、客户端只读"。
- **影响面**：`GameSnapshot`（+1 字段）、`MatchHost`（单机填双 View）、`ArenaOl`（1 个属性改为按座位取）。**很小。**

### T2 · 座位 ↔ 会话（唯一的安全边界变更）

- **现状**：`MatchHost._seatToSession/_sessionToSeat` 双向 1:1（`MatchHost.cs:44-45, 176-202`）；`IntentHub.HandleIntent` 强校验 `intent.PlayerId == seat`（`IntentHub.cs:69-77`），这是防"代对手操作"的核心防线。
- **方案（推荐）**：**不改 `MatchHost` 的默认语义**，新增 `Script/Net/Godot/LocalHotseatMatch.cs`：
  - 内部复用同一套装配，但座位解析改为"以 `intent.PlayerId` 为准"，一个本地会话同时持有 1/2 两座位；
  - 决策请求按 `request.PlayerId` 定向投递给**同一个**本地 UI（UI 靠 `PlayerId` 区分"该谁点"）。
- **红线（必须写进代码注释与评审清单）**：
  - 该放宽**只允许**在单机进程内路径生效；`LobbyServer` / `StartServerOnly` / 任何网络会话**禁止**使用；
  - 不得通过一个 `bool` 参数挂在 `MatchHost` 上让网络路径"理论上能传 true"——用**独立类**把风险关进一个文件。
- **影响面**：新增 1 个文件（约 150–250 行），`MatchHost` 零改动。

### T3 · 决策请求的接受与超时

- **现状**：
  - `ClientMatchView.HandleMessage` 直接丢弃 `req.PlayerId != LocalSeat` 的请求（`ClientMatchView.cs:266`）；
  - `NetworkInputGateway.TimeoutSecondsFor` 按类型 30–60s 自动取消（`NetworkInputGateway.cs:85-112`），`TimeoutProvider` 返回 ≤0 会回退默认值（`:123,146`）。
- **方案**：
  1. 单机 `LocalSeat = 0` 表示"同桌"，此时**接受任意座位**的请求；`ArenaOl.OnClientChoiceRequest` 本身无座位过滤，天生可用。
  2. 决策窗口标题带"玩家 1 / 玩家 2"（`ChoiceRequest.PlayerId` 已足够）。
  3. **超时改为"本地不限时"**：需让 `TimeoutProvider` 支持"永不超时"语义（当前 ≤0 会被吞成默认值，必须显式支持，例如返回 `-1` 表示不设超时；直接传 `int.MaxValue` 会溢出秒→毫秒）。
- **风险**：若漏掉第 3 点，单机玩家思考超过 30–60 秒会被**自动取消**，表现为"我还没点，选择就没了"——这是统一后最容易出现的"新单机 bug"。

### T4 · `_localPlayerId` 的一肩三职拆分（改造主体）

`ArenaOl` 里 `_localPlayerId` **出现 58 次、`ViewMirrored/ViewCtr/HandCtr/DeckZoneOf…` 31 处**，它同时承担：

| 语义 | 例子 | 同桌模式下应改成 |
|---|---|---|
| ① 视角（牌摆哪、谁在下） | `ViewMirrored = _localPlayerId == 2`（`:70`）、`ViewCtr`（`:73`） | `_viewSeat = 0` → **关闭镜像**，座位1 恒在下 |
| ② 身份（上行用谁的名义） | `SendIntentAs(_localPlayerId, …)`、`DoPass/DoEndTurn`（`:4547,4554,4563`） | **按被操作对象决定**（卡 `inst.ControllerId` / 按钮自带座位） |
| ③ 输入门（谁能拖/点） | `ui.CanDrag = isLocalHand && …`（`:4450`）、`IsLocalPlayer(p)` | 两副手牌都可拖，**由服务端裁决**（与单机今天的行为一致） |

- **方案**：拆成 `_viewSeat`（0 = 同桌不镜像）/ `_identitySeat`（单机=viewSeat；同桌=按操作对象）/ `_actorSeat`（高亮/文案/让过按钮）。
  **默认值保持"三者都等于 localSeat"→ 联机行为零回归**，这是这次改造能安全落地的关键。
- **场景缺口（实测 diff，必须补）**：`ArenaOl.tscn` 比 `Arena.tscn` 少 `OpponentPassButton`、`EndTurnButton` 两个节点，`Arena.tscn` 含 `GameInitializer` 节点。
  - 而 `ArenaOl._Ready` 用 `GetNodeOrNull` 绑 `ActionPanel/EndTurnButton` → **静默为 null**。
  - 结论：单机切到 ArenaOl 后，"玩家2 让过"没有按钮、结束回合键缺失 → **功能倒退**，必须补节点 + 按座位绑两个让过键。
- **影响面**：`ArenaOl` 58 处逐点判定归属（机械但要细），`ArenaOl.tscn` 补节点。**这是本次改造的主要工作量。**

### T5 · 手感：全量重建的最后一公里

- **现状**：每次快照 → `ApplySnapshot` → `RebuildDecks/Graveyards/Assets/AreaZoneCards/Attachments/Score/Stack/Councils` → 卡片 UI 全部销毁重建；`SnapshotApplicationQueue` 允许合并与最长 1.5s 延后（`ArenaOl.cs:190-196`）。
- **风险**：单机从"事件增量（改 1 张卡）"变成"每步重建全桌（20–40 张卡 × PackedScene 实例化）"。桌面大概率可接受；**Web（wasm、threads 模型）上有明显卡顿与 hover/拖拽被打断的风险**。
- **方案（按性价比排序）**：
  1. 进程内直投**快照对象**（不经 JSON 字符串），省掉整局快照的序列化/反序列化（实测整局约 103 KB）；
  2. 按 UID **复用 CardUI**：只有"新增/移除/换容器"才重建，纯状态变化（横置/伤害/正反/费用）只更新字段；
  3. 保留**乐观回显**（已有先例：`TryOptimisticEchoHandLimitDiscard`），让高频动作"点了立刻有反应"；
  4. 用已有 `VerbosePresentation` 加"应用快照耗时"埋点，持续观测。

## 4. 可行性判定

| 项目 | 判定 | 依据 |
|---|---|---|
| 架构上能否统一 | ✅ 成立 | 两条链路的"客户端半边"已经是同一个 `ClientMatchView` + `IMatchClientView`，`ArenaOl` 已经能挂两种来源（`AttachMatchClient`/`AttachSession`） |
| 是否要重写渲染 | ❌ 不需要 | `ArenaOl.tscn` 由 `Arena.tscn` 复制，布局同源；ArenaOl 已覆盖全部 `ChoiceRequest.Kind`（含 `ChoicePromptPanel` 兜底） |
| 热座是否可行 | ✅ 可行，工作量中等 | 行动者可从"卡所属座位"推断（与单机今天完全一致）；需拆 `_localPlayerId` 三职 + 补 2 个按钮 |
| 是否引入安全风险 | ⚠️ 有，但可隔离 | 仅 T2 一处；用独立类 + 禁止网络路径引用即可 |
| 是否影响规则层/测试 | ✅ 基本不影响 | 规则层与意图层不动；受影响的是 UI 层测试与"依赖 Arena 场景"的用例 |
| 是否会让单机变慢 | ⚠️ 可能 | 全量重建开销，需 P0 实测后决定策略 |

**结论：技术上成立，风险集中且可隔离，主要成本在"手感"与"58 处身份判定"这两处细节。**
没有发现"必须先解决才能做"的架构死结。

## 5. 分阶段实施计划

### P0 · 量化实验（先量再改，1 个实验，不改产品代码）

- 用 `LoopbackTransport + MatchHost + ClientMatchView + ArenaOl` 跑一局脚本化对局（20–30 步），埋点记录：
  1. `BuildSnapshot` 耗时；2. 序列化 + 反序列化耗时；3. `ApplySnapshot` 耗时；4. `ArenaOl` 全量重建耗时；5. 峰值内存增量。
- **桌面 + Web 各跑一次**（Web 是关键，wasm 上重建开销完全不同）。
- 产出：一张数字表 + 判定"全量重建是否可接受 / 是否必须先做 UID 复用"。
- **决策门**：若 Web 单步 > 50ms → 先做 T5-1/T5-2 再继续；否则按原计划推进。

### P1 · 布局共用件（低风险，立即收益）

- 把"给定模型状态 → 容器内子节点集合与顺序/位置"抽成 `ArenaPresenter`（纯函数式），`Arena` 与 `ArenaOl` 都调它。
- 目标不是"两套合一套"，而是先让**摆放/布局规则只有一份**（历史 Layout 类 bug 最容易两边各写一份）。
- 验收：`P5LayoutMathTests` / `DeckBoardLayoutTests` 全绿，且双端截图/节点序列一致。

### P2 · 双端对拍机制（这是"修一次两边都对"能长期成立的唯一保障）

- 新增回归：同一组脚本化操作，分别在 ① `Arena` + 真实 Manager ② 本机 `MatchHost` + `ClientMatchView` 下执行；采集"UI 状态快照"（每张卡的 zone / 容器 / 顺序 / 位置 / 正反 / 横置 / 标签文本 / 高亮集合），逐项比对。
- 现状基础：`ClientServerParityTests` 已证明"逻辑层对拍"可行，本阶段把它扩展到**表现层**。
- 价值：即使将来不统一，也能持续暴露"两边不一样"的具体点位。

### P3 · 本地同桌通道（新增文件，不改默认语义）

- `LocalHotseatMatch`：一个本地会话 ↔ 两个座位；不过滤快照 + 双 View；决策请求按 `PlayerId` 投递；超时不生效。
- 用**独立调试入口**（如 `--arena=snapshot` 或主菜单隐藏入口）先跑通，不动正式单机入口。

### P4 · `ArenaOl` 泛化 + 单机切换（灰度）

- 拆 `_viewSeat / _identitySeat / _actorSeat`；补 `OpponentPassButton` / `EndTurnButton`；两副手牌可拖。
- 灰度：`--arena=legacy|snapshot` 开关，默认仍 legacy；两个版本并行一轮（用 P2 对拍兜底）。
- 回滚点：开关切回 legacy 即可，风险可控。

### P5 · 手感补齐与退役

- T5 的三项优化；动画/悬停/拖拽细节回归。
- `Arena` 降级为调试/对照场景（或直接删除），**净减约 5778 行渲染代码**。

## 6. 风险与代价（必须提前接受的部分）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 权威边界被放宽 | T2 是唯一"安全事故级"变更 | 独立类、网络路径禁止引用、评审清单强制检查 |
| Web 手感倒退 | 全量重建 + 快照体积 | P0 先量化；UID 复用；进程内直投；乐观回显 |
| 单机短期不可用 | 切换期间交互细节回归 | 灰度开关 + 保留 legacy 一轮 |
| 测试迁移 | 依赖 Arena 的 UI 测试（badge peek/布局/拖拽等） | 跟随 P4 迁移；规则层测试不受影响 |
| "继承联机的坑" | ArenaOl 自己也有大量"对齐单机"的补丁；统一后这些补丁成为唯一实现，好坏一起继承 | P2 对拍 + P5 逐条验收 |
| 收益被高估 | 统一只解决"渲染/交互分叉"，**不解决**"服务端投影字段缺失"这一类联机 bug | 明确预期：目标是"修一处两边生效"，不是"两边零 bug" |

---

## 7. 替代方案对比（先别急着全量统一）

| 方案 | 内容 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A 全量统一**（本文主线） | 单机 = 本机权威 + 投影 + `ArenaOl` | 高（P0–P5） | 渲染真正只有一份，长期维护成本减半 | 中（灰度可控） |
| **B 只共用表现层** | 抽出 `ArenaPresenter`，两条数据通路保留 | 中（P1） | 吃掉约 60–70% 的"布局/摆放分叉" | 低；但"时序/合法性"类分叉仍在 |
| **C 只做对拍** | 不动架构，只加双端比对回归 | 低（P2） | 持续暴露差异，避免"改一边忘另一边" | 最低；但每个差异仍要修两遍 |
| **D 单机改为"内嵌服务端 + BOT/单人"** | 放弃同屏热座，直接复用「建立主机」 | **接近零** | 天然与联机完全一致 | 极低；**但产品形态变了** |

> **D 值得单独提出来**：如果"单机"的产品定义其实是"一个人自己练/打 AI"，那根本不需要热座统一——现有「建立主机」+ `LoadBotRunner` 已经就是"完全一致的联机链路"。这是性价比最高的选项，取决于单机是否必须保留同屏双人。

**推荐组合**：`P0（量化）+ P2（对拍）` 立即做；`P1（共用件）` 视 P0 结果做；`A ≠ 全做` 时优先 D。即：
**先花很小成本把"差异看得见"建立起来，再决定要不要付"统一"的大钱。**

## 9. 方案选定（2026-10-19）：方案 E · 单进程双客户端分屏热座

### 9.1 决策

**单机模式的定位 = 测试夹具**（只为在不启多个进程的前提下复现/定位 bug），**且同屏双人不可放弃**。
在这个前提下，最合适的**不是** A（单视图上帝视角），**也不是** D（放弃热座），而是本文档此前未展开的第五个选项：

> **E：一个进程内起 1 个本地权威服务端 + 2 个标准联机客户端，两个 `ArenaOl` 实例左右分屏并排，各自"本方在下"。**

在 `MatchHost + LoopbackTransport + 2 × ClientMatchView` 之上装两个 `ArenaOl` 实例。**渲染代码 = 联机渲染代码，逐字节相同。**

### 9.2 为什么"测试夹具"这个定位让 E 从备选变成唯一优解

| 判据 | A（单视图上帝视角） | **E（双客户端分屏）** | D（弃热座） |
|---|---|---|---|
| 同屏双人 | 需改造（双 View + 双身份） | **天然满足**（两个视角本就各自"本方在下"） | ❌ 不满足 |
| 单机能测出联机的 bug | ⚠️ 引入"不过滤快照 / 上帝视角"这个联机**不存在**的模式 → 测出的 bug 可能联机不复现 | ✅ **100%**：同一 `ArenaOl`、同一 `ClientMatchView`、同一 `MatchHost`、同一快照过滤、同一决策归属、同一超时 | ✅ |
| 是否新增"仅单机存在"的分支 | 是（不过滤 + 双 View + 双身份） | **否，零新分支** | 否 |
| 需动 `_localPlayerId` 58 处 | 是 | **否** | 否 |
| 需动 `GameSnapshot` / 双 View | 是 | **否** | 否 |
| 需动座位↔会话 1:1 安全边界 | 是（T2） | **否** | 否 |
| 新增代码量 | ~1500 行改造 + 补 tscn 节点 | **~600–700 行新增，既有代码仅改 1 处** | ~0 |
| 屏幕信息 | 一份战场 + 双方明牌 | 两份战场，各看自己视角（对手手牌为牌背，符合真实对战） | — |

**决定性理由**：单机作为测试夹具，唯一有价值的东西是"它跑的是联机那条路"。A 为了把两个视角塞进一个视图，必须新增"不过滤快照 / 双 View / 双身份"三处联机永不使用的分支——**测试夹具一旦和被测对象产生分叉，它的结论就不再可信**。E 是唯一能让"单机复现 = 联机复现"成立的选择。

### 9.3 三个硬点在 E 下直接消失（这是成本差的主要来源）

| 原硬点 | 在 E 下为何不存在 |
|---|---|
| **T1 热座双视角 / 双 View** | 每个客户端实例收到的仍是**按自己座位过滤**的快照（`MatchHost.PushSnapshot` 原样工作）。P1 实例看到自己的手牌明牌、P2 的手牌牌背；P2 实例反之。两副手牌在**两块屏幕上**都可见，不需要任何"双 View"或"不过滤快照"。`GameSnapshot` 零改动。 |
| **T2 座位 ↔ 会话 1:1** | 一个客户端 = 一个会话 = 一个座位，**比例仍是 1:1**。`IntentHub.HandleIntent` 的 `intent.PlayerId == seat` 校验原样生效，且天然通过（每个 `ClientMatchView` 的 `BindSender` 用自己的 `LocalSeat` 上行）。**安全边界一点不动。** |
| **T4 `_localPlayerId` 一肩三职** | 职责没变，因为实例里只有一个身份。P1 实例 `localSeat=1`（`ViewMirrored=false`，本方在下）；P2 实例 `localSeat=2`（`ViewMirrored=true`，本方在下）。视角/身份/输入门三者仍相等——**这正是联机的语义**。58 处一处不用改。 |

`ArenaOl` 同时被证实**可多实例**：零 `static` 可变状态、零 `GetTree().Root` / group 全局查找、零 `GameInitializer` 依赖、零 `UiNotificationBus` 使用（自带 `OnlineNoticeWindow`）；所有节点用相对路径 `GetNodeOrNull` 解析，`AttachMatchClient(client, localPlayerId)` 本身就是注入接缝。

### 9.4 E 唯一必须改的既有代码：决策超时

`ClientMatchView` 丢弃非本座位请求 → E 下天然正确，不用改。
`NetworkInputGateway.TimeoutSecondsFor` 的 30–60s 自动取消 → **夹具下必须可关**，否则"想久了选择自己消失"。

现状：`TimeoutProvider` 返回 ≤0 会被吞成 `DefaultTimeoutSeconds`（`:146-147`），所以"不限时"不能用 0 表达。改法（约 5–10 行）：给 `-1` 显式语义 —— 返回 `-1` 时不创建 `System.Timers.Timer`（等同 `Timeout.InfiniteTimeSpan` 语义），并加注释说明只有本机夹具允许使用。**这是整个方案对生产路径的唯一触点，且默认值不变 → 联机零回归。**

**先 E 后（可选）A，而不是直接 A。**

### 9.9 追问：分屏会不会"天然和单屏不一致"？

**结论：布局不会。** 但这个直觉指出的方向是对的——分屏确实会引入一类"单屏绝不出现"的新 bug，只是**不在布局上**，而在**进程级共享状态**上。逐项排查如下。

#### A. 布局为什么不会分叉（四条硬证据）

| # | 事实 | 含义 |
|---|---|---|
| 1 | `project.godot`：`window/size/viewport_width=1920`、`viewport_height=1080`、**`stretch/mode="viewport"`** | 整个 UI 渲染在**固定 1920×1080 的逻辑视口**里，`GetVisibleRect()` 与物理窗口尺寸无关 |
| 2 | `ArenaOl.tscn` 共 19 个锚点节点：**9 个绝对 offset**（`Player1Area`/`Player2Area`/`CenterArea`/`HandContainer` 固定 `240→1200`/`AssetContainer` 固定 `1500→1900`…）、**9 个全拉伸**（根节点、`ArrowLayer`、各 `CardContainer`…）、**1 个比例锚点**（仅 `ActionPanel`，`0.896→0.969`） | 绝对 offset 不读视口；拉伸节点的父容器都是固定尺寸；`ActionPanel` 虽随视口变，但视口锁 1920 后结果与全屏完全相同 |
| 3 | 全场景 9 个 `anchors_preset=15`（拉伸）节点里，除根节点与 `ArrowLayer` 外，其余（`AreasContainer`、各 `CardContainer`）父容器都是固定尺寸 | 拉伸节点跟着"已固定的父"走，结果仍是固定 |
| 4 | `ArenaOl` 中 9 处 `GetViewport().GetVisibleRect().Size` **全部**用于窗口居中 `(vp - win.Size)/2`；手牌横向排列用 `_areasContainer.Size.X`（=`CenterArea` 的 1920×540），不用视口宽 | 没有任何一处"按视口宽重排战场"的逻辑 |

> **实施红线**：每个 `SubViewport.size` 必须**固定 `1920×1080`**，只缩放它的显示。这样根 Control 尺寸恒为 1920×1080，全部绝对 offset 与拉伸节点的父尺寸都不变 ⇒ **布局代码走的是与全屏逐字节相同的路径**，唯一差别是最终像素被等比缩小。
>
> **绝对不能**为了"自适应"把 `SubViewport.size` 设成 `960×540`——那样根 Control 只有 960 宽，`AssetContainer`（x=1500）整块落在视口外被裁掉、`CenterArea` 右半消失。这才是真正的分屏 bug，而且很容易在第一版实现时踩到。

#### B. 已扫出的真实冲突：`CardPreviewBus` 静态总线（必须修）

`Script/UI/CardPreviewBus.cs` 是**静态类**，`CanPreview` / `Overlay` / `ViewerPlayerId` 三个静态字段，`Attach()` 的注释原文就是"重复调用＝覆盖，**后装配的视图生效**"。

两个 `ArenaOl` 同存时：
- 后 `_Ready` 的实例把 `Overlay` 指到自己 → 在 P1 战场悬浮卡片，浮层弹进 **P2 的 SubViewport**（或相反），位置对不上、甚至看不见；
- `CanPreview` 的查看者口径被覆盖 → P1 可能按 P2 的座位判定"这张牌能不能看"（`CovertInspectRule.CanViewerSeeCardFace` 的 viewerId 错了）；
- 先退出的实例 `Detach()` 会把另一个实例的注册一起清空。

**这是分屏引入的、单屏绝对不会出的 bug。** 修复不难：`ResolveOverlay` 已经实现了"按节点所属视口/窗口找自己的浮层"（`node?.GetWindow()?.GetNodeOrNull(...) ?? Overlay`），把它从 `GetWindow()` 扩展成按 **`GetViewport()`** 查表（`Dictionary<Viewport, Entry>`）即可，约 30 行；保留静态 `Overlay` 作为查不到时的兜底 ⇒ **单机全屏零回归**。

好消息：工程在"去静态化"上已经做过大扫除（`EffectEngine`/`CardManager`/`GameInitializer` 注释里多处"原 static 字段改实例"）。全工程静态可变字段除 `CardPreviewBus` 与各 Manager 的 `Instance`（两个 `ArenaOl` 都不创建 Manager，不会覆盖）之外没有新的。`ArenaOl` 本身：0 个 static 可变状态、0 处 `GetTree().Root`/group 查找、0 处 `UiNotificationBus`、不依赖 `GameInitializer`。

#### C. 输入映射（有风险，但可实测）

`ArenaOl` 用 `GetGlobalMousePosition()`（3 处）+ `_UnhandledInput` 事件分发。`SubViewportContainer` 会把鼠标事件转发进 SubViewport 并换算坐标，`GetGlobalMousePosition()` 在 SubViewport 内返回**该视口自己的**坐标 ⇒ 天然正确。
真正的风险在"逻辑 1920 缩到 960 显示"这一步的**坐标反变换**：`Control.Scale=0.5` 方案在 Godot 4 中会带进 input transform，理论正确；但拖拽跨帧（按下→移动→松开）任一帧错位都会表现为"牌拖不动 / 落点偏"。**这是 M2 第一件要实测的事**，也是三条实现路径（`Control.Scale` / `TextureRect + 手动 PushInput` / 自定义 Container）的选型依据。

#### D. 验收：把"分屏不许有自己的 bug"变成自动红灯

新增**三端对拍**：同一组脚本化操作，在 ① 全屏单客户端 ② 分屏左 ③ 分屏右 各采一份 UI 状态快照（每张卡的 zone / 容器 / 顺序 / 位置 / 正反 / 横置 / 标签文本 / 高亮集合），逐字段比对。
任何"只在分屏发生"的布局或状态差异都会直接报红，而不是靠人眼看。这是把用户的担心制度化。

#### E. 退路：零布局改动的退化形态

若 M2 实测发现输入/缩放代价过高，退化为：**一个全屏战场 + `F1/F2` 切换 + 另一方信息摘要条**。
两个客户端仍然都在跑、都能操作（各自收自己的快照和决策请求），只是同一时刻只完整显示一个视角。此形态**不缩放、不改布局**，分屏特有 bug 类直接归零，代价是"两块完整战场同时可见"的体验让步。

#### F. 一句话回答

> 分屏**不会**让布局和单屏不一致——因为这个项目的 UI 从设计上就只认 `1920×1080` 逻辑坐标，不看物理窗口。
> 它**会**让"进程级共享状态"暴露出来：单屏时全世界只有一个视图，写死单例也不会出错；分屏时同时有两个视图，`CardPreviewBus` 这类静态总线立刻冲突。这类问题数量有限（已扫出 1 个）、边界清晰、修法明确，属于**一次性成本**，而不是持续分叉。

### 9.10 操作便利性：让过是高频动作，不该被"视角"绑架

#### 痛点成立，而且有代码级证据

用户指出的"分屏/切换下让过操作不便"不是主观感受，`ArenaOl.tscn` 里能直接看到原因：

| 事实 | 后果 |
|---|---|
| `ActionPanel` 是**全场景唯一一个比例锚点节点**（`anchor_left=0.896, anchor_right=0.969`），让过键 `PassButton` 和投降键 `ConcedeButton` 都在它里面 | 分屏到 960 宽时，面板宽度从 ~140px 缩到 **~70px**，两个按钮挤不下；位置也偏到半屏右上角，需要瞄准 |
| 分屏下**两个半屏各有一套 `ActionPanel`**，但只有当前行动者那套有效（`DoPass` 里 `IsLocalPlayer` 会拒掉另一个） | 屏幕上有两个"让过"，其中一个点了没反应——高频操作最怕这种"点了不知道有没有生效" |
| 切换模式（F1/F2）下，若当前显示的不是行动者视角，**必须先切视角再点** | 一次高频动作变成三步 |

#### 关键事实：让过和结束回合是同一个意图

`ArenaOl.cs:4558 / 4568` —— `DoPass(playerId)` 与 `DoEndTurn(playerId)` **发的都是 `PlayerIntent.Kind.Pass`**。规则层里"让过/推进阶段"只有一种动作。

单机之所以有两个按钮（`OnPlayerPass`→`Pass(1)`、`OnOpponentPass`→`Pass(2)`），是因为**一个视图要同时代表两个人**，必须让玩家指定替谁点。热座下两个真人都在场，**按钮语义就应该是"当前行动者让过"，一个就够**。

而"当前行动者"现成可读，不需要新增字段：`GameSnapshot.PriorityPlayerId` + `CurrentPhase` + `TurnCount` 都在快照里（`GameSnapshot.cs:22-24`），`ClientTurnManager` 投影后直接可取。

#### 更正（2026-10-19）：让过不是本作的特殊设计，MTGA 一模一样

前一版把"让过是秒级高频动作"当成我们的独有约束，这是错的，必须改正：

- **MTG 规则层**：`CR 117.3d` 有优先权者选择不行动即 *pass*；`CR 117.4` 全体连续让过 → 结算栈顶或结束该步骤/阶段。也就是说**每个步骤双方都要各让过一次**，一回合十几个窗口，频次和我们同级甚至更高。
- **我们的实现**：`TurnManager.Pass`（`Script/Manager/TurnManager.cs:929`）与上述规则一一对应——A 让过 → 行动权显式交给 B；`_passedPlayers.Count >= 2` → 堆叠非空则 `ResolveStackTop()`，堆叠空则 `AdvancePhase()`。机制上与 MTG 无差别。
- **MTGA 的交互**：让过从来不是"每个玩家各有一个按钮"，而是**一个固定位置的上下文按钮**，标签随状态变（`Pass` / `Next` / `Resolve` / `Pass Turn` / `Combat`）；`空格` = 过优先权，`回车` = 过回合，`Shift+回车` = 无条件过回合；**没有任何可行动作时引擎自动跳过**（auto-pass），`Ctrl` / `Ctrl+Shift` 才是"全控制"，点阶段条可设 `stop`；对手在考虑时显示 priority hold。

⇒ 三条结论：

1. **§9.10 的设计不需要"发明"，照抄即可，而且比原来更简单**：不是"两套按钮"也不是"每人一个让过"，而是**一个**上下文按钮，绑定 `PriorityPlayerId`，标签按状态切换（让过 / 推进 / 结束回合并示意下一步）。原估的 120–160 行里，有一半是在处理"两个座位两套按钮"，现在可以砍掉。
2. **"让过变便宜"的真正杠杆是 auto-pass，不是更好的按钮**。而我们的代码里**没有 auto-pass**：`_passedPlayers` 只在显式调用 `Pass()` 时增长，没有任何"该玩家无合法动作 → 代其让过"的分支。所以夹具里如果觉得让过点得烦，正确解法是在规则层加"无合法动作自动让过"（`LegalityProjection` 已经是现成的判定源），**两种模式同样生效、不产生分叉**。
   > 但这是一条独立的**规则层**改动（会改变对局观测到的窗口数量，MTG 里也因此需要"全控制"来对冲信息泄露），**不要混进本次"渲染统一"里**。先记录，单独评估。
3. 上一版"交接屏在此必然失效"的**结论仍然成立，但理由换掉**：不是因为"我们让过更频繁"，而是因为**让过是每步骤都发生的**——交接屏适合"一整个回合交接一次"的粗粒度（见 §10.3），任何每步骤都要遮一次屏的设计都会把对局切碎。MTG 不需要交接屏，是因为两个玩家各有一块屏。

#### 设计：全局常驻操作条（不属于任何 ArenaOl）

```
┌────────────────────────────────────────────────────────────────────┐
│  玩家 2 行动中 · 主阶段 · 第 3 回合      上一次：玩家1 让过          │
│                                                                    │
│              [ 让过 / 推进  ␣空格 ]        [ 投降 ]     视角 自动 ⇄ │
└────────────────────────────────────────────────────────────────────┘
```

- **只有一个主按钮，标签随状态切换**（`让过` / `推进阶段` / `结束回合`）——与 MTGA 同款。不做"玩家1让过""玩家2让过"两个按钮：那等于把单机历史包袱搬进热座
- **主按钮 = 让过/推进**，绑 `空格`（最高频动作给键盘，连按无副作用——服务端对非法 Pass 会拒，不会重复结算）
- 点击走 `activeArena.DoPass(activeSeat)` —— **与联机按钮完全同一条路径**，连 `DoPass` 内部的模态检查（`_activationSelectionBusy || _noticeWindowOpen` 时禁止让过）都自动继承，不会出现"决策窗开着还能让过"的新 bug
- `activeSeat = snapshot.PriorityPlayerId`（回退 `FirstPlayerId`，再回退 1）
- 视角默认 **自动跟随 `PriorityPlayerId`**；`F1`/`F2` 临时锁定看某一方，`F3` 回自动
- **`ArenaOl` 零改动**：夹具场景里把 `ActionPanel` 直接 `Visible = false`，让过入口由全局条接管

#### 顺带解决了归零缩放的诉求 → 默认单屏，分屏为可选模式

两个客户端实例 + 两套 SubViewport **都常驻**（这本就是方案 E 的架构），"单屏/分屏"只是切换 `Visible`，不重建、不重新 Attach、瞬时生效：

| 模式 | 说明 | 风险 |
|---|---|---|
| **单屏（默认）** | 只显示 `activeSeat` 那个 SubViewport，全屏 `1920×1080` | **零缩放、零布局改动、零输入坐标换算** ⇒ §9.9 的 C 项风险直接消失 |
| **分屏（可选，`F9`）** | 两个并排缩放显示 | 保留，用于"需要同时看两边"的场合，走 §9.9 的缩放方案 |

> 组合起来：**操作靠常驻条（一次点击/一个空格），视觉默认不缩放（零分叉风险），分屏退化为可选增强。** 这就是"操作便利"与"布局零风险"同时成立的那个解。

> **分屏的信息暴露（2026-10-19 补测）**：`SnapshotFilter.IsPlayerOwnedHiddenZone` 只对 `Hand` 做按座位隐藏，对手手牌被替换成 `hidden_*` 占位（无 `TemplateUid`）。所以分屏时左半屏是"P1 真手牌 + P2 牌背"、右半屏是"P2 真手牌 + P1 牌背"——**两个人同框时等于互相明牌**。这与 legacy 单机现有行为一致（`Arena` 本来就是双方手牌都正面，只有 `IsCovert` 暗藏卡盖背），对"测试夹具"不构成回归，甚至更方便验证；但若将来要做"两人同屏正常对局"，这里必须加明牌开关或交接遮罩，不能算已经解决。

#### 成本

| 项 | 规模 | 是否改动既有代码 |
|---|---|---|
| `HotseatActionBar`（**单个**上下文按钮 + 视角跟随 + 键位 + 座位/阶段标签） | ~90–120 行 + 场景节点（比原估少，因为不需要"两套按钮"分支） | **否** |

**M2 的形态因此调整为：单屏 + 常驻操作条（先行，风险最低），分屏作为 `F9` 增强后置。** 这样即使分屏的输入映射实测不顺利，主体功能也不受影响。

## 10. 业界参照：成熟产品怎么做单机测试（2026-10-19 调研）

> 结论先给：**MTGA 没有"单机测试"这回事——因为它根本没有离线的单机模式。** 所有对局（含单人打 AI）都跑在服务端。我们的问题类别在它那里被架构性地消除了，不是被"测试得好"解决的。

### 10.1 MTGA：客户端瘦、权威永远在服务端

据 Wizards 官方规则团队开发者公开撰文（*On Whiteboards, Naps, and Living Breakthrough*，作者 Alex Werner）：

- 追踪对局状态、执行规则的组件叫 **GRE（Game Rules Engine）**，用 **C++ + CLIPS（LISP 变体）** 写成；
- 客户端是**瘦客户端**：只上行动作、只按服务端下发的状态渲染，不在本地跑规则；
- 多人来源一致确认 MTGA 是 **online-only**：连单人模式（打 Sparky / 教程）也在服务器上跑，断网即不可玩。

⇒ **它只有一条渲染路径**，因为只有一种"权威位置"。所谓"单机 vs 联机不一致"这个 bug 类别，在 MTGA 的架构里没有产生的土壤。

⇒ 反过来说：**把"服务端"搬进同一个进程（本地方案 E）在架构血统上是正统的**，不是妥协。MTGA 的"权威在服务端"和我们的"权威在本地进程内"，只是部署位置不同，客户端契约完全一样。

### 10.2 可以直接借鉴的一点：GRE 的"白板" = 我们的 `LegalityProjection`

官方文章对 GRE 的描述里有一句关键的话（原文）：

> "one of the things the GRE is constantly doing is assembling a list of **available actions for a player who has priority**"

它把这份清单写在"白板"上（`AVAILABLE ACTIONS FOR PLAYER 1`），然后各张卡的 CLIPS 规则往白板上增删（例如 Meddling Mage 会把 `Cast Lightning Bolt` 从清单里擦掉），GRE 醒来后只执行白板上的内容。

**这正是我们 `MatchHost.BuildLegalityView(seat)` → 快照 `View` → `ArenaOl.ClientLegalityView` 在做的事**：服务端算好"这个座位此刻能做什么"，客户端只读、不重算。

所以本文 §3-T1 里坚持的"**单机也不能让客户端本地算合法性**"，不是我们自己想的补丁——它和业界最强实现是同一个设计。`ClientServerParityTests` 记录的历史坑（JC005/JC020/JC068/JC001：客户端本地算 → 输入缺失 → 两端结论不同）本质上是**重走了 MTGA 早就绕开的弯路**。

### 10.3 同屏热座：MTGA 给不了答案的部分，其实只有"共用一块屏"

MTGA 不做同屏热座（隐藏信息 + 商业上要卖两份），所以"同屏双人"这件事在竞技卡牌里没有先例。它的行业参照在桌游数字化：

| 行业通行做法 | 出处/表述 |
|---|---|
| **只有一个设备、一个视图**，屏幕上只出现当前行动者的盘面 | "only the active player's board is ever on screen"（Deck Builder Pass & Play 文档） |
| **交接屏（hand-off screen）**：结束回合 → 全屏遮罩盖住盘面 → 点名"请把设备交给 X" → 下一位主动确认（有的要求长按）才揭开 | 多款 Pass & Play 产品的标准设计；有产品文档明确把"点一下就好、还会闪一帧上屏"列为**弱实现** |
| **回合长度是筛选器**：私有回合太长，等待的人就变成"拿着别人手机的观众" | "Turn length is the filter"（culi.app 对 one-phone 游戏的分析） |

**这两条对我们的直接印证**：
1. 上一轮定的"**单屏 + 自动跟随视角**"正是行业标准形态，分屏不是。用户对 F1/F2 的直觉与行业一致。
2. 行业里之所以能靠"交接屏"解决隐藏信息，前提是**交接颗粒度 = 一个私有决策段**（桌游是"一整个回合交接一次"）。而我们的让过是 `CR 117` 层面的**每步骤优先权交替**（机制与 MTG 完全同构，见 §9.10 的更正）——一回合十几个窗口，每个都要交接一次屏，对局会被切碎。
   > **注意别误读**：这不代表"我们比 MTG 更快、所以更难"。MTG 的让过频次和我们同级甚至更高，它处理得毫无压力——**因为它不需要交接屏，两个人各有一块屏**。差异不在节奏，在"共用一块屏"。

### 10.3.1 更正：让过这件事，MTGA 是现成参考答案

前一版把"让过"写成了本作的独有难点，这是错的。MTGA 的让过交互非常明确，且与 §9.10 的设计完全同构：

| MTGA 的做法 | 说明 |
|---|---|
| **一个固定位置的上下文按钮** | 标签随状态变：`Pass` / `Next` / `Resolve` / `Pass Turn` / `Combat`。**从来不是"每个玩家一个让过按钮"** |
| **`空格` = 过优先权** | 等价于点 `Next`；最高频动作给了键盘 |
| `回车` = 过回合 / `Shift+回车` = 无条件过回合 | 因为 MTG 区分"过优先权"和"过整个回合"；我们的 `Pass` 已统一两者，所以只需要 `空格` |
| **无可行动作 → 自动跳过（auto-pass）** | 引擎代玩家让过。这是真正把让过频次压下去的手段 |
| `Ctrl` / `Ctrl+Shift` = 全控制；点阶段条设 `stop` | 反向开关：想看更多窗口时用，代价是暴露"我手里有东西" |

⇒ 所以"常驻按钮 + 键盘"不是我们发明的形态，**是从 MTGA 直接搬过来的**。这让 §9.10 的风险大幅下降：按钮行为有成熟实现可对照，`空格` 键位也不是拍脑袋。

⇒ 同时也暴露了一件独立的事：**我们的代码里没有 auto-pass**（`TurnManager.Pass` 只在显式调用时累加 `_passedPlayers`）。所以夹具里"让过点得烦"的根因不在按钮形态，而在缺这一层。它是**规则层**改动、两模式同源，但会改变对局观测到的窗口数量，应单独立项，不混进本次渲染统一。

### 10.4 反面案例：客户端权威的代价

MTGO（Magic Online）是更老的架构，客户端持有完整对局状态、本地执行规则。它长期被"信息泄露 / 客户端状态可被操纵"困扰，这个教训直接推动了 MTGA 走向"客户端零规则"。

**我们现在的 legacy 单机就是客户端权威**——只是因为没有对手，作弊问题从未暴露。但它一旦被当作联机基础，就会立刻撞上同一堵墙。所以"统一到服务端权威"不只是为了测试方便，而是**把架构从 MTGO 式迁到 MTGA 式**。

### 10.5 对标能给我们什么、抄不到什么

| | 内容 |
|---|---|
| **能抄** | ① 权威只有一份，客户端零规则（MTGA 的 GRE 模式）② 服务端算"可用动作清单"，客户端只读（GRE 白板 = `LegalityProjection`）③ 让过 = **单个上下文按钮 + `空格`**，标签随状态切换（MTGA 交互模型，直接搬）④ 热座用单视图 + 视角跟随，不用分屏（桌游 Pass & Play 标准）⑤ 离线单机 = 同一套客户端 + 把权威放本地（Asmodee 系桌游的单人模式即如此） |
| **抄不到** | **没有成熟产品同时需要"两个行动者共用一块屏 + 各自隐藏信息"**。竞技卡牌（MTGA / MTGO）不做热座——它靠"每人一块屏"从物理上消除了这个组合；桌游热座有隐藏信息，但交接颗粒度是"一整个回合一次"，靠交接屏就够。我们是这个组合的交集：**共用屏 + 隐藏信息 + 每步骤交替的让过**，三者同时成立时既不能分屏（互相明牌）、也不能每步交接（切碎对局），只能靠"单视图 + 自动跟随 + 全局按钮"自解，并用 §9.9-D 的三端对拍兜住 |

> 一句话：**架构和交互都抄 MTGA（权威唯一、客户端零规则、单按钮 + 空格让过），真正要自己解的只有"共用一块屏"这一件事。** 上一版把"让过"也算进"抄不到"，是错误的自我加码——那部分恰恰是最有参考答案的。
