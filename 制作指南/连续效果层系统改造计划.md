# 连续效果「统一属性账本」改造计划

> **文件名沿用历史**（《连续效果层系统改造计划.md》曾被 `JCContinuousGrantAuditTests` 的已知缺陷说明引用）；
> **本版口径（用户 2026-10-16 澄清）已不再采用万智式分层**——本项目**不需要"层"**，需要的是
> **一套统一的属性加减计算方法**：所有属性走同一套账；复杂计算只落在**四条基础属性（调查 / 战斗 / 势力 / 防御）**
> 上；控制权 / 类别 / 领域 / 关键字等**只是"授予 / 剥夺"条目**，与数值同账本、同一次重算，但**不参与求和**。
> 文中的"层"字样一律读作"**账本条目类**"。
>
> **规则既定点（用户确认，无争议）**：**能力图标即属性**——
> 黑刀＝战斗、白刀＝先手战斗、黑眼＝调查、白眼＝先手调查、黑星＝势力、白星＝先手势力
> （单一映射表 `EffectEngine.IconToAttribute`）。故"授予图标"与"授予属性"**是同一次写入**，
> 不存在"要写两遍"的规则。（**防御**没有对应图标，直接以属性表达；【心】【血】【死】【星】等是
> **魔法领域图标**，与能力图标是两条轴，卡文自己也区分，见 JC101/JC066 的括注。）
>
> 本文＝**现状缺陷（可执行证据）→ 目标模型（统一账本 + 一次重算）→ 逐卡清单 → 改动范围（P0/P1/P2）→ 验收锚点**。

## 一、现状缺陷：为什么会出现"图标 / 属性两本账"

**规则只有一本账，代码却有两本**——这才是要修的东西（不是规则有疑问）：

| 事实 | 代码位置 | 后果 |
|---|---|---|
| `CardInstance` 维护**两个集合**：`_grantedIcons`（`HasIcon` 查它）＋ `_grantedAttributes`（数值查它） | `CardInstance.cs`（`Grant/Revoke` 的 `case "Keyword"/"Icon"/"Attribute"`） | 同一个"黑刀"要被写两遍才完整 |
| **动作通道 `Gain` 自动折算**（同时写 Icon + Attribute） | `EffectEngine.ApplyGain`（4471–4484） | 行为正确 |
| **形态通道 `FormChangeSpec.Grants` 自动折算** | `EffectEngine.ApplyFormGrants`（4694–4700） | 行为正确 |
| **持续通道 `ContinuousGrants` 不折算**（原样 `Grant`） | `EffectEngine.RegisterPersistent`（7535–7541） | 卡脚本**必须手写 `Icon:X` + `Attribute:<对应属性>` 两条**；漏写一半 ⇒ 静默不一致 |
| `Icon` 通道**几乎无消费者**（只有持续授予自愈判定 `IsGrantPresent` 与测试读 `HasIcon`；卡面 UI 渲染的是调/战/势**数值**） | — | 漏授**既不报错、界面也看不出来** ⇒ 长期潜伏 |

**已查出的不一致（可执行证据）**

| # | 卡 | 卡文（`.tres`） | 脚本实际授予 | 缺 |
|---|---|---|---|---|
| 1 | **JC018** 魔刃传人 | "你的资产区内每有一个【心】，魔刃传人**就获得一个［黑刀］**" | `Attribute: 战斗 ×1` | ❌ 无 `Icon:黑刀` |
| 2 | **JC030** 巨型蝙蝠 | "…则巨型蝙蝠**获得［黑眼］**，并额外具有吸血鬼类别" | `Attribute: 调查 ×1` + `SubCategory: 吸血鬼` | ❌ 无 `Icon:黑眼` |
| 3 | **JC085** 复生行尸 | "…则复生行尸**获得［白星］**" | `Attribute: 先手势力 ×1` | ❌ 无 `Icon:白星` |
| 4 | **JC060** 神秘学顾问 | "所有未印刷有魔法领域图标的本方角色**获得【心】图标和［黑刀］**" | `Icon:心` + `Attribute: 战斗` + `MagicDomain:Mind` | ❌ 无 `Icon:黑刀` |

> 这 4 处已固化为 `JCContinuousGrantAuditTests.TestAudit_卡文能力图标与脚本授予一致`（以 `.tres` 卡文为判据，
> 首轮即报 4 处），并以 `[KnownDefect]` 标记（可见、不拖红主线）。

**另一处同源缺陷（JC105 × JC106）**：`ReplaceIcon` / `IconSuppression` 的操作对象是**属性**且**两种基数混用**
（`势力` 取 `CurrentPower` 含印刷值，其余取 `GetAttribute(...)` 只含授予表），并**不写** `Icon:黑刀`：

```
[EffectEngine] ⇄ 图标替换：探针 的 [白星]×1 → [黑刀]（直到回合结束）
[DIAG] 替换前 势力=0 先手势力=1；替换后 势力=0 先手势力=1 仍有白星=True 有黑刀=False
```

⇒ 卡文说"**所有［黑星］和［白星］能力图标都替换为［黑刀］**"（对象是**图标集合**），
代码做的是"对**当前数值**做一次反向加减"，于是：① 替换后白星还在（光环自愈按"目标仍符合光环条件"又补授回来）；
② 黑刀也没留下（基数错）。这是**增量施加**必然带来的**顺序依赖**缺陷。

## 二、目标模型：一本账 + 一次重算（`Recompute`）

### 2.1 账本条目（唯一真相源）

每条连续/静止效果登记**若干条目**，条目字段：

| 字段 | 说明 |
|---|---|
| `Kind` | 条目类：`Attribute` / `Icon`（＝Attribute 的别名写法）/ `Keyword` / `SubCategory` / `SubCategoryRemove` / `MagicDomain` / `StaticRule` / `Control` / `Rewrite`(改写) / `Suppress`(失去) |
| `Value` | 属性名或条目标识（属性名一律用**规范名**：调查/战斗/势力/先手调查/先手战斗/先手势力/防御） |
| `Amount` | 数值（正负皆可；非数值条目忽略） |
| `Source` | 来源（卡 UID + 效果 Id），用于撤销、自愈与"是否仍在账本"判定 |
| `ExpireTurn` | 时效（"直到回合结束"），到期条目在重算时被丢弃 |

### 2.2 重算（唯一入口）

```
Recompute(card):
    条目全集 = 账本(card) 的当前有效条目（未到期、来源在场/条件成立）
    条目全集 = 施加"改写 / 失去"过滤器（Rewrite / Suppress）      ← 关键：作用于**集合**，不是作用于数值
    card.CurrentInvestigation = 印刷值 + Σ条目(调查)  …（战斗/势力/防御 同）
    card.CurrentFirstStrike…  = 印刷值 + Σ条目(先手调查/先手战斗/先手势力)
    card.HasIcon(X)           = (Σ条目(IconToAttribute(X)) > 0)
    card.HasKeyword / 子类别 / 魔法领域 / 静止规则 / 控制权 = 直接读同一次集合
```

### 2.3 四条不变式（改造的验收标准）

| # | 不变式 | 为什么需要 |
|---|---|---|
| ① | **重算幂等**：`Recompute(card)` ×N 结果不变 | 杜绝"自愈补授把东西补回来/重复扣减"（JC085/JC089 这类历史坑） |
| ② | **顺序无关**：先 A 后 B ≡ 先 B 后 A | 对抗结算与"谁先发动"解耦（本次 JC105/JC106 的核心要求） |
| ③ | **改写是过滤器**：`替换为/失去` 对**条目集合**施加，再求和 | JC106"白星→黑刀"：无论光环何时补授，结果恒为"无白星、+1 黑刀" |
| ④ | **自愈＝"该条目是否仍在账本"**（不是"目标是否仍符合条件"） | 被改写/被抑制的贡献**不再被补回来** |

> 这四条正是"统一属性加减"与"万智式分层"的差别：**本项目不需要层与层之间的相互覆盖规则**，
> 只需要"**每次从账本重算一次**"——顺序问题在模型层面就不存在。

## 四、改动范围（三档，供裁定）

### P0 — 最小可交付（建议先做；直接修掉已查出的不一致，并为统一账本铺路）

| 项 | 改动点 | 规模 |
|---|---|---|
| ① 统一"图标→属性"折算 | `RegisterPersistent`（7535–7541）补折算；三处折算收口为同一实现（单一映射 `IconToAttribute`） | 引擎 2 处（补 1 + 收口 1） |
| ② 修 4 张漏授图标的卡 | JC018 补 `Icon:黑刀`、JC030 补 `Icon:黑眼`、JC085 补 `Icon:白星`、JC060 补 `Icon:黑刀`（或由 ① 自动折算出图标/属性任一侧） | 卡脚本 ≤4（或 0，若 ① 双向折算） |
| ③ 修 JC106 的改写语义 | `ReplaceIcon` 改为"**条目集合过滤器**"：把 {黑星,白星} 的**图标贡献**整体投给 黑刀；产出 `Icon:黑刀`；幂等；到期无损还原。`ReapplyIconSuppressions`（JC123）同口径 | 引擎 1 处 |
| ④ 修光环自愈判据 | 由"目标仍符合光环条件"改为"**该条目是否仍在账本**"（`IsGrantPresent` / `ReevaluateAuras` 收口） | 引擎 1 处 |
| ⑤ 防回归 | `JCContinuousGrantAuditTests`（以卡文为判据）＋ `[KnownDefect]` 锚点 `TestB4_8A`（JC105×JC106）**已先行落地** | 测试 1 套（已完成） |
| ⑥ 去冗余（可选） | 14 张成对写 `Icon`+`Attribute` 的卡删掉冗余行（JC001·016·019·028·037·045·051·073·082·084·089·105·109·116） | 卡脚本 ≤14（建议留到 P1） |

**风险：低**——①④⑤ 只改"图标账"；②只**补**图标（数值不变）；③只改 JC106 一条效果；`Icon` 通道当前无 UI 消费者。

### P1 — 账本地基（**零行为变更**）

- 新增 `Script/Data/Effects/AttributeLedger.cs`：条目结构 + 过滤器 + 排序/失效规则；
- `EffectData` 增 `LedgerEntries`（由卡文措辞推导；引擎侧只看"是否数值 / 是否过滤器 / 是否特征"三类信息）；
- `EffectEngine` 新增 `Recompute(card)` / `RecomputeAll()`，把现存 **E1–E5 五个重算入口**收敛为 1 个：
  `RegisterPersistent` / `UnregisterPersistent` / `ReevaluatePrereqs` / `ReevaluateAuras` / `ReapplyIconSuppressions`
  （另补审计发现的 4 处次序隐患：`ReevaluatePrereqs` 提前 return、`RealignAllContinuousGrants` 漏 `ReapplyIconSuppressions`、
  `CardManager.RevealCard` 漏先手值重算、`Arena` 侧 View 重算）；
- 验收：现有 `156 套件 / 1334 例` **全绿且数值零变化**。

### P2 — 逐项落地

- 数值属性**只由账本推导**（卡脚本可只写图标，属性自动折出）；
- `AreaStatsCalculator.ValueOf` 改为消费账本结果（其形态已是"实例总值 + 先手授予"）；
- **C/S 投影同步扩字段**：`GameSnapshot` / `RenderCommand` / `ZoneManager.ProjectCard` /
  `CardInstance.RestoreProjectedState`（客户端不跑 `EffectEngine`，账本输出必须投影，否则两端不同解）。

### 不动的范围（边界）

触发类效果（一次性，不入账本，除产生持续效果者如 JC106 改写 / JC008 时效授予）；
L0 类**消费者**（只改"注册 / 重算"，不改消费者：`UntapAll` / `AreaStatsCalculator` / `CombatManager`…）；
秘社 `CouncilStatic` / `OpeningEffectList`；构筑级规则（JC125）；费用修正栈（旁支 E）。
