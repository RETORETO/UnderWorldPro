# 双端一致性（单机/联机同一套规则判定）

> 现行有效版。定位：**加新效果/新限制、改快照字段时必读**的约束文档。
> 配套回归测试：`Script/Tests/ClientServerParityTests.cs`（已注册进 `TestsRunner`）。

---

## 一、原则

**规则判定只有一份实现，两个执行端共用；差异只允许出现在"输入从哪里来"。**

- 单机：View（`Arena`/`CardDragController`）与服务端 Manager 同进程，输入=本局 Manager 实例。
- 联机：服务端用同一批 Manager 判定；客户端要么读**服务端算好的结论**（合法性投影），
  要么用**同一份规则函数 + 随快照投影过来的输入**判定。

禁止：客户端另写一份判定逻辑、客户端自己枚举候选范围、规则函数在缺输入时静默给出 false/0。

## 二、客户端侧的三层结构（`ArenaOl`）

| 层 | 位置 | 说明 |
|---|---|---|
| ① 服务端投影（首选） | `GameSnapshot.View`（`GameViewSnap`） | 服务端用生产规则函数算好的 `ActivatableUids` / `AbilityTargets` / `PlayTargets`；客户端只做成员判断 |
| ② 同一规则函数 + 投影输入（兜底） | `IsActivatableForClient` / `IsLegalPlayTargetForClient` / `ComputeLegalCardTargetUids` | 无投影（旧服务端/测试）时执行；输入由 P1 的快照字段补齐 |
| ③ 共享静态函数 | `DeployCovertEligibility.IsEligible(inst, deployCovertBlocked)` | 服务端喂权威封锁态，客户端喂 `PlayerManager.IsDeployCovertBlockedProjected` |

投影生成入口：`Script/Manager/LegalityProjection.Build(...)`，在 4 处下发点接线
（`GameInitializer.BuildSnapshotFor`、`MatchHost.PushSnapshot/PushSnapshotToSeat`、`NetworkMatchLauncher.PushSnapshotLegacy`）。

## 三、加新东西时的检查清单

1. **新增 `TargetRestriction` / 目标条件**：只改 `TargetValidity.CheckRestrictions` 一处。
   若该条件读了**运行时状态**（本局 Manager、静止标记、授予、子类别…），必须确认这些状态在下列二者之一里：
   - 随快照投影（见 §四），或
   - 由服务端投影直接给结论（`GameViewSnap`，客户端根本不需要该状态）。
2. **新增 `StaticKind` / 持续效果授予**：默认会被 `ZoneManager.ProjectCard` 自动带走（静止标记/授予/子类别/先手值）。
   若引入**新类别**的运行时状态（新字段），在 `ZoneCardRef` + `ZoneManager.ProjectCard` + `CardManager.RebuildFromRef`
   （`CardInstance.RestoreProjectedState`）三处补齐——**这是唯一允许的投影入口，不要在别处手写映射**。
3. **新增"玩家级封锁/限制"**（如 JC068 封锁派遣）：不能只写在服务端动作里，否则客户端会放行到服务端才被拒。
   做法：权威值进 `PlayerSnapshot`（见 `DeployCovertBlocked` 范式），客户端读投影值喂给同一判定函数。
4. **不要给规则函数加静默兜底**：`pm == null → return 0/false`、`EE != null && …` 这类写法会让"客户端缺输入"
   表现成"规则不满足"，且单进程测试（静态字段被同进程服务端顺手填上）测不出来。缺输入必须告警（见
   `TargetValidity.HasMindDomain` / `EffectEngine.GetPrereqLoyaltyValue`）。
5. **跑 `ClientServerParityTests`**（`TestsRunner` 内含）：它对"手牌×场上目标"与"激活效果×目标"做全矩阵比对
   （服务端 / 客户端本地 / 服务端投影 三者必须相等），并对已知偏差点位（JC005 有【心】、JC020 装备结附、
   JC068 封锁、JC001 白眼）加显式期望值。新增状态未投影时，这里会红。

## 四、快照投影字段（P1）

`ZoneCardRef` 目前承载：区域/朝向/横置/伤害/创伤、`CurrentInvestigation/Strength/Power/Defense`、
`MagicDomains`、`EnteredThisTurn`、`VersionId`、`AbilityUsedThisTurn`，
以及**运行时状态补全集**：`StaticFlags`、`SubCategories`、`GrantedKeywords`、`GrantedIcons`、
`GrantedAttributes`、`CurrentFirstStrikeInvestigation/Strength`。

回填纪律（`CardInstance.RestoreProjectedState`）：**直接覆盖，不走 `Grant()`**——
`Grant` 对"调查/战斗/先手调查"会就地叠加 `Current*`，而 `Current*` 已随快照独立投影到位，再走 Grant 就二次叠加。

## 五、已知边界（有意为之，勿误判为缺陷）

- **原子锁（`TurnManager.IsAtomicLocked`）不下发**：快照可能在服务端原子段内生成，下发"锁"会让客户端
  卡在"永久锁死"（后续无快照解锁）。故投影生成时用 `CanActivate(..., ignoreAtomicLock: true)`
  绕开时序门禁——时序由服务端在意图入口强制，不属于"规则合法性"。
- **行动次数（派遣/资产）不下发**：客户端目前无消费者；若将来要在客户端置灰，走 `PlayerSnapshot` 补字段。
- **"打出"卡级门禁（档位/阶段/优先权）客户端不预判**：单机同样只由 `TurnManager.PlayCard` 拒绝，
  两端行为一致（拒绝后由 UI 提示）。若要客户端预置灰，需在 `GameViewSnap` 增补 `PlayableHandUids`。
- **激活的地区目标（`TargetKind.Area`）联机仍不支持**：`ArenaOl.SendActivation` 明确拒绝；单机支持。
  当前无任何已实现效果使用该形态；接入时需同时补"地区候选投影 + 服务端 `ActivateAbility` 地区目标路径"。
