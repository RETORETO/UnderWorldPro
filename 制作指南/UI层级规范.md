# UI 层级（ZIndex）规范

> 适用范围：战场表现层 `Arena`（单机）/ `ArenaOl`（联机）及其下所有卡牌、附属、封印、箭头、浮层、调试命令框。
> **唯一真相源：`Script/UI/Layers.cs`。任何 UI 元素都从这里取层号，禁止再写魔数。**

## 一、为什么要统一

1. **Godot `z_index` 有硬上限 ±4096**，超出会被引擎截断/丢弃。历史上曾出现
   "命令框设 `ZIndex = 4100` 却仍被秘社卡压住"——根因不是排错方向，而是 **4100 已越过上限**。
2. 层级此前散落各处（`100` / `1000` / `4095` / `4096` / `4100` …），想在"某两层之间插入新东西"必须先全工程翻一遍，
   改一处极易踩到另一处。
3. 统一后全部层级落在 **0 ~ 1000**，并显式留出**带间空档**，后续扩展无需再压缩。

| 400–499 | 卡牌**拖拽态** | `CardDragging` = 400 |

### 关键相对关系（改层号时必须保持）

```
所有卡牌(≤399，含状态角标 380~399) < 拖拽中的卡(400)
              < 箭头(800) < 卡面悬浮预览(830) < 结果标签(850) < 统计标签(860)
              < 区域张数角标 ZoneCountLabel(890，绝对层) < 命令框(900)

分数区里"赢取地区"的卡面(300~340) < 牌库/墓地面板 ZoneContainerPanel(350) < 张数角标(890)
  ⇒ 2026-10-20 用户口径：分数区层级必须低于卡组/墓地（双方都是）；
    牌库/墓地面板要压住分数区，但**不能高过拖拽层 400**（否则拖拽中的卡会钻到面板底下）。

（2026-10-16 修正：原式曾写作"…< 附属(500) < 封印(550) < 箭头(800)…"。附属/封印本就
 不占固定层、走"宿主层 − 偏移"（见下节），500/550 只是常量命名与预留；角标方案定稿后该带
 整体腾空，故从本式中移除。若在**任何**地方看到"附属(500) < 封印(550)"的固定高低表述，
 以本节与本式为准 —— 该关系不存在。）
```

压缩**完整保留**了原有相对高低：旧值箭头 4095 < 预览 4096、统计 600 < 结果 4096 < 命令框（4100，被截断到 4096）。
唯一因越界而必须修正的是命令框：`4100 → 900`，它现在**真正**高于结果标签与悬浮预览。

### 附属 / 封印的特殊约定

> **【2026-10-16 状态】** 本节描述的是**旧承载方式**（实例级偏移布局）。按 `UI美化与空间重排方案.md`
> 决策 3：**"结附/封印于卡"（cat-2）改为宿主卡角标 → 走 380~399，不再使用偏移法**；
> **"结附/封印于地区"（cat-1）继续在地区容器内平铺**（用地区容器自身的层级，同样不使用本偏移）。
> 即：本节的偏移公式在角标方案落地后**将无使用者**，`AttachedBadgeBase`/`SealedBadgeBase` 随之变为纯预留。
> 保留本节仅作历史说明与"宿主可能是卡牌也可能是秘社"这一背景知识的记录。

附属与封印**不占固定层**，而是"相对宿主层级做偏移"：
`附属层 = 宿主层 - (序号 + 1)`、`封印层 = 宿主层 - 1 - 序号`。
原因：宿主可能是卡牌（300~399）也可能是秘社（同样 300~399），偏移法能自动跟随宿主，
不会出现"宿主是秘社时附属跑到世界层"的问题。`AttachedBadgeBase` / `SealedBadgeBase`
仅作为"该不该用偏移法"的文档标记与未来固定层场景的预留。

**补充（2026-10-16，配合 `UI美化与空间重排方案.md` 决策 3）**：

- **角标 → 380~399**：封印/附属折叠为宿主卡上的"数字角标"后，角标**不再走相对偏移**，
  而是取**卡牌本体带末尾的预留区间**（见 `Script/UI/Layers.cs:18` 的 ★扩展 注释：
  "卡面装饰、状态角标 → 380~399"；本文件第二节分带表的 300–399 行已登记同一区间）。
  角标紧贴卡牌本体（≤399），远低于拖拽层（400），拖拽时仍被拖动卡压住 —— 符合直觉。
- **500~599 带将腾空**：折叠后实例级附属/封印不再需要中间层（仅 cat-1「结附/封印于地区」继续在
  地区容器内平铺，走的是地区容器自身层级）。该带整体释放，留给后续"依附类"新元素。
- **展开浮层**：角标 hover 展开的多卡面板走**浮层带**（`CardHoverPreview = 830` 或其并列分支），
  **不占用** 500~599。
- 因此**不存在**"附属(500) < 封印(550)"这种固定高低关系；若在别处看到该表述，以本节为准。

**实施订正（2026-10-18，P3a 已落地，与此前计划不同）**：

- **角标实际采用"宿主相对层"，不取 380~399 绝对层**。原因：角标是**宿主卡的子节点**，
  用绝对层 380~399 时两张卡的角标会处在同一层、按树序互压 ⇒ 出现"被压在下面那张卡的角标浮在上面那张卡上"。
  现实现为 `ZAsRelative = true` + `ZIndex = 1`（`Script/UI/CardBadges.cs`）：
  角标永远压在自己卡面之上、又跟随宿主的相对层序，语义等价且不会跨卡乱序。
- **380~399 仍保持预留**，留给"不依附于单张卡"的卡面装饰（状态图标等）。
- **角标可点区域只覆盖右下角**（`MouseFilter = Pass`）：既收 `mouse_entered/exited` 做 hover 展开，
  又不吞掉卡片点击。展开面板走浮层带 `CardHoverPreview = 830`（`Script/UI/CardBadgePeek.cs`）。

**实施订正·续（2026-10-18 用户口径：角标分家 + 双击激活）**：

- **「封×N」与「附×N」是两个独立命中区**，根节点 `__CardBadges` 改成 `MouseFilter = Ignore`（只做布局），
  两个 `Label` 各自 `Pass` + 各自 `mouse_entered/exited`，回调携带 `CardBadgeKind`
  （`CardBadges.OnBadgeHover(host, kind)`）。原因：封印卡与附属卡来自**两个不同区域**，
  混在一排里玩家会选错对象；悬浮哪一类就只展开那一类，面板标题直接写「封印卡」/「附属卡」。
- **展开面板里的卡双击＝发动激活能力**（`CardBadgePeek` 的 `mb.DoubleClick` → `onActivate`）：
  附属/封印被折叠成角标后场上已无卡面可双击，`JC020 引匕的飞刀` 这类 `AttachmentActivated` 能力
  会彻底变成死卡。双击**必须复用既有双击链路**（单机 `_onAttachmentDoubleClickedForward`、
  联机 `OnAttachmentDoubleClicked`），不得另开通道绕开门禁/日志。
- **计数与列表同源**：`CollapseOneHost` / `RefreshHostBadge` 统计与展开面板过滤都用
  `ReferenceEquals(m.AttachedTo, host)` / `ReferenceEquals(s.SealedBy, host)`，
  否则会出现"角标写附×2、面板只列 1 张"。回归由 `Script/Tests/BadgePeekTests.cs` 锁定。

## 三、模态窗口为什么不占这张表

调查/战斗/破平/触发排序/选目标等弹窗的根节点都是 Godot **`Window`**（独立子窗口），
引擎保证它们永远渲染在所有 `Control` 之上。因此：

- 它们**不消耗** 0~1000 的预算；
- 其内部子控件的 `ZIndex` 只需在**该窗口内部**保持相对高低，使用**独立的小整数命名空间**
  （见 `TriggerOrderWindow.tscn` 的 `OrderZoneContainer = 1000`、`DoneButton = 100`）；
- 窗口内的"拖拽条目"需要用窗口局部的高层号：`Layers.TriggerOrderDrag = 1500`（仅窗口内生效）。

## 四、新增 UI 元素的标准流程

1. 在 `Layers.cs` 里找到**用途最接近的那一带**，优先用该带的空号（表中【预留】已标出区间）。
2. 若该带排满，用**带间空档**：`199→200`、`299→300`、`399→400`、`499→500`、`599→600`、`699→800`、`899→900`。
3. 在 `Layers.cs` **补一个具名常量**，注释写清它与相邻常量的高低关系。
4. 使用处只写 `Layers.XxxName`，**不写字面量**；场景文件（`.tscn`）里的 `z_index` 同步改成该常量对应的数值，
   并在本文件第二节的表格里登记。
5. 若新元素要压在某个已有元素之上，先确认第二节"关键相对关系"是否仍然成立；不成立就必须在计划里说明原因。

## 五、排查"某元素被压住"的步骤

1. 先确认它的 `z_index` **是否超过 4096**（超了就是被引擎截断，改层号即可）。
2. 再确认它和遮挡者的**父链是否同级**：`ZAsRelative = false` 的节点用绝对层号，
   与相对层号节点比较时以"绝对层号"为准。
3. 若是 `Window` 内容被挡，问题一定不在全局层级，而在该 `Window` 内部子控件的相对层级。
